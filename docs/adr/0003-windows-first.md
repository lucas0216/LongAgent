# ADR-0003 · MVP 仅做 Windows，Mac 推迟到 v1.5

**状态**：✅ Accepted
**日期**：2026-05-27
**决策者**：产品负责人

## 背景

我们用 Tauri 理论上可以一份代码跑 Win/Mac/Linux。MVP 阶段是否双端齐发？

## 决策

**MVP（v1.0）只发 Windows 版本。Mac 版本推迟到 v1.5（预计 M7-M9）。Linux 不计划。**

## 理由

### 目标用户的设备分布

主画像 P1（办公小白）：
- **Windows 占比 80%+**
- Mac 用户偏极客，不是 P1 主体

学生群体：
- Win 占 70-80%
- Mac 占 15-25%

**结论**：先抢 80% 的用户，Mac 是放大器而非引擎。

### 双端齐发的代价

| 项目 | 单端 | 双端 |
|---|---|---|
| MVP 周期 | 4 个月 | 5.5-6 个月 |
| UI 测试工作量 | 1x | 2x |
| 打包 / 签名 / 发布 | 1x | 2x |
| 客服 / Bug 修复 | 1x | 1.5x |
| Mac 特有问题（TCC 权限、Notarization）| 0 | 显著 |

**节省下的 1.5-2 个月**可以做：
- 产品打磨
- 用户访谈和迭代
- 内容营销准备

### Mac 用户的"等待"成本可接受

- Mac 用户群体小但忠诚
- 给一个"v1.5 上 Mac"的明确预告，转化等待为期待
- 反而可以做"Mac 抢先体验 Wait List"营销

### 风险控制

集中精力把 Windows 做到极致，胜过双端都半成品。

## 权衡（接受的代价）

| 代价 | 缓解 |
|---|---|
| 错过 Mac 用户的早期口碑 | v1.5 前用 Wait List 收集 |
| Mac 用户社区曝光（极客圈影响力强）| 用 X / Twitter / Hacker News 在 v1.5 集中爆发 |
| 团队 Mac 经验积累延后 | M0 还是要打通双端 PoC（保证后续不返工）|

## 重要约束（不能违反）

为了 v1.5 顺利上 Mac，**MVP 开发期间必须**：

- [ ] 所有代码不写死 Windows 路径分隔符（用 `std::path::Path`）
- [ ] 所有 UI 在 CI 上的 macOS runner 跑截图测试
- [ ] 文件操作通过 Tauri FS API（不用 winapi）
- [ ] 不依赖 Windows-only 库（除非有明确替代）
- [ ] Mac PoC 在 M0 第 1 周完成（双端 HelloWorld）
- [ ] 每个 Sprint 末有 Mac 构建检查（不一定测全功能，但保证能构建）

## 不选其他方案的理由

### 不选 "双端齐发"

理由见上：周期 +50%，团队风险大。

### 不选 "仅 Mac 优先"

- Mac 用户基数小 5-10 倍
- 我们的 Aha Moment 是"小白也能用"，Mac 用户偏极客，Aha 效应弱

### 不选 "先 Linux 极客版"

- 用户基数 < 5%
- 与产品定位（小白）矛盾

## 上线后的 Mac 计划

| 阶段 | 时间 | 内容 |
|---|---|---|
| Mac PoC 维持 | M0-M4 | CI 构建 + 偶尔抽查 |
| Mac Wait List | M4 起 | 官网收集 Mac 用户邮箱 |
| Mac Alpha | M7 | 邀请 100 个 Wait List 用户测试 |
| Mac Beta | M8 | 扩大到 1000 |
| Mac 正式版 | M9 | App Store + 官网下载 |

## 后果

### 正面

- 产品周期可控
- 团队专注一个平台
- 上线后能集中支援

### 负面

- 早期失去 Mac 用户的高质量反馈
- Mac 极客圈影响力延迟产生
