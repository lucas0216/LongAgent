# ADR-0006 · Browser Use / Computer Use 推迟到 v1.5

**状态**：✅ Accepted
**日期**：2026-05-27
**决策者**：产品负责人

## 背景

Browser Use / Computer Use 类技术（让 AI 控制浏览器或电脑界面）已经成熟：

- browser-use（GitHub 50k+ stars）
- Anthropic Computer Use API
- Stagehand、Skyvern、ByteBot、OpenInterpreter

竞品 Marvis 主打这个能力。我们要不要在 MVP 就做？

## 决策

**MVP（v1.0）不做。v1.5 起以"白名单场景"形式做，永不做开放式 GUI 自动化。**

## 理由

### 技术可行性不是问题

Tauri 不限制 browser use（详见对话讨论）—— browser use 是另起独立 Chromium 进程，与 App 自己的 WebView 无关。Python sidecar 直接 import browser-use 即可。

**技术成本 ≈ 200 行代码 + 首次启动下载 Chromium。**

### 真正的阻塞是 5 个产品/商业理由

#### 1. 成本结构

| 任务类型 | 单次成本 | L2 月费 ¥29 够跑 |
|---|---|---|
| 纯文本任务 | ¥0.01-0.05 | 数百次 |
| Browser use（含 vision）| ¥0.3-1.5 | 15-60 次 |
| Computer use | ¥0.5-3 | 6-40 次 |

L2 用户每天用 2 次就把订阅费跑光。**我们要么贴钱，要么涨价（小白跑了）**。

#### 2. 可靠性不达可用阈值

- browser-use 公开 benchmark 成功率 60-75%
- 中国互联网（验证码、风控、SPA、登录态）再砍 20-30%
- **实际成功率 40-50%**

参考 Marvis 实测：微博签到 3 分钟还不一定成功。

**小白对失败的容忍 = 0**。失败一次就卸载。

#### 3. 信任飞跃太大

| 权限 | 小白心理门槛 |
|---|---|
| "AI 读我桌面的 Excel" | 😐 还行 |
| "AI 控制我浏览器" | 😨 它会乱点吗？|
| "AI 控制整个电脑" | 😱 它会转我钱吗？|

Marvis 有腾讯品牌做缓冲，我们冷启动期没有。**一个负面新闻能直接杀死产品**。

#### 4. 战略定位会撞死

做了 → 与 Marvis、Manus、Genspark、豆包桌面版**正面打**。
- 他们：大厂、有钱、有模型、有渠道
- 我们：小团队、零起步

**不做 → "我们只做文件，但做到极致" 是清晰定位。**

#### 5. 开发资源吞噬 MVP

Browser/Computer use 的"做好"工程量 ≈ 再做一个完整产品：
- 跨平台 Accessibility 适配
- 不同网站反爬应对
- 任务中断/恢复/暂停
- 失败重试 / 错误兜底
- 用户安全确认机制
- 隔离沙箱

**用同样 4 个月做文件场景能做到行业最好，做 browser use 做到 60% 可用。**

### "永不做开放式"的理由

即使到 v2/v3，我们都**不打算**做"通用的让 AI 操作任何浏览器/任何应用"。理由：

- 开放式失败率高 → 信任损耗
- 不可逆操作的红线（发邮件、转账、删数据）
- 真正高价值的自动化都有 API/CLI 路径

**我们的路线**：场景化"狭义 Agent"——为特定高频场景做高可靠流程，而不是给用户一把开放的枪。

## 替代方案：v1.5 的白名单 Browser Use

### 设计原则

- 仅支持**预先内置且测试过**的 5-10 个场景
- 不是"通用 browser use"，是**"场景插件"**
- 每个场景成功率必须 > 90%（不达标就不上）
- 用户视觉可见浏览器在做什么（透明）
- 任意时刻可中断

### 候选场景（优先级）

| 场景 | 价值 | 难度 | 优先级 |
|---|---|---|---|
| 12306 抢票 | 极高 | 中 | P0 |
| 政务办事大厅 | 高 | 高 | P1 |
| 个人所得税 APP/网页 | 高 | 中 | P1 |
| 社保查询 | 中 | 低 | P0 |
| 医院预约挂号 | 高 | 高 | P2 |
| 银行账单导出 | 中 | 高 | P2 |
| 招聘投递批量 | 中 | 中 | P1 |

### 实现策略

```
v1.5 阶段:
- 集成 browser-use 库
- 但只暴露"场景插件"UI（不暴露通用 browser use）
- 每个插件：固定的 prompt + 预测试的网站 + 兜底处理
- 用户不能"自由"指令浏览器
```

## 不选其他方案的理由

### 不选 "MVP 就做开放式"

5 个理由全成立。

### 不选 "永远不做"

会失去能讲的能力故事；放弃这类需求会被对手抓走。

### 不选 "只做 computer use 不做 browser use"

- computer use 失败率比 browser use 高 30%+
- browser use 有 DOM 可解析，更可控

## 风险

### R-1：用户在 MVP 期间问"能不能做 X 网站"

**应对话术**：
> 这个能力我们将在 v1.5 上线。当前版本专注做好文件场景，敬请期待。

预留 Wait List 收集需求。

### R-2：竞品做出可靠 browser use

应对：
- 跟进时只做最高价值场景，不追求广度
- "成功率高"和"场景聚焦"仍是差异化

### R-3：技术成本下降很快

如果半年内 token 单价降 5 倍 + 可靠性升到 80%+，提前到 v1.2 上 browser use。

## 后果

### 正面

- MVP 范围清晰，4 个月可达
- 不需要承担可靠性失败的口碑风险
- 集中资源做文件场景到极致

### 负面

- 早期失去能"演示酷炫"的卖点
- 部分用户失望（但他们本来也不是我们 MVP 的目标）

## 验证计划

MVP 上线后收集：
- [ ] 用户问"能不能做 XX 网站"的频次
- [ ] 高频请求场景排序
- [ ] 用作 v1.5 白名单优先级输入
